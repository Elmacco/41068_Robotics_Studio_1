## Current status

The assignment work lives in `ros2_ws/src/41068_assignment/` (its own [README](ros2_ws/src/41068_assignment/README.md) has full run instructions — this is just the summary). The whole demo starts with `ros2 launch 41068_assignment demo.launch.py`, plus the dashboard page served from `GUI/`.

- **Sim**: Will's `simple_trees` world (raised hiking trail, trees, launch pad, four people, one in a red shirt) with the Parrot drone spawned on the launch pad. Everything the demo uses is inside `41068_assignment`; most of it started as copies from `41068_ignition_bringup`.
- **Sensors**: RGB-D camera (tunable FOV/tilt), lidar, IMU and a thermal camera in which people are warmer than trees and grass, all bridged to ROS.
- **Navigation**: localisation from odometry + GPS (EKF), so the map frame is the world frame (`slam:=True` runs SLAM Toolbox instead). Nav2 flies the drone, and `flight_controller.py` holds its altitude.
- **Mission modes** (`mission_manager.py`, commands on `/parrot1/mission_command` or the dashboard buttons): **Mapping** explores the world on its own and builds a terrain map from the depth camera (ground height, obstacles, trails). **Passive** patrols a detected trail at 0.8 m. **Active** flies to each person found, checks they are warm in the thermal camera, and checks whether their shirt is red from close up, then Passive carries on. The terrain map also gives **ranger routes**, the least-effort walking path to any point (`/parrot1/plan_ranger_route`, or click the dashboard map).
- **Detection**: YOLO finds people in the RGB image, the thermal camera confirms body heat, and the depth camera places them on the map (`points_of_interest`).
- **Dashboard**: browser page with the top-down terrain map, RGB and thermal feeds, telemetry, mode buttons, manual control and a "Person found" alert.
- **Settings**: the key mission and detection parameters are in `config/mission.yaml`; per-world settings are in `config/worlds/<world>.yaml`.
- **Not done**: flying over hills (needs height-above-ground control), following a route through the trail network rather than one trail section.

This package is under active, ongoing development by multiple people — see the workflow rules below before pushing changes to it.

## Two repositories in this workspace

This project actually involves **two independent git repositories**:

1. **This repo** (`41068_robotics_studio_1`) — shared assignments, lab notes, and any packages authored for the subject. This is the one hosted at `github.com/Elmacco/41068_Robotics_Studio_1`.
2. **`ros2_ws/src/ros_tutorials/`** — a plain `git clone` of the upstream [`ros/ros_tutorials`](https://github.com/ros/ros_tutorials) repo (branch `humble`), used to read/run the official ROS 2 tutorial packages (`turtlesim`, `roscpp_tutorials`, `rospy_tutorials`, etc.).

They are **not** linked as a git submodule — `ros_tutorials` is just a second, self-contained repo that happens to live inside this repo's working tree, and it's excluded via `.gitignore` so this repo's git never tries to track its contents. Because of that:

- `git status`/`git add`/`git commit` in the top-level repo never touch anything inside `ros_tutorials/`.
- Inside `ros2_ws/src/ros_tutorials/`, `git` commands operate on the *upstream* repo's history (`origin` = `github.com/ros/ros_tutorials`), completely separate from this repo's history/remote.
- To pull the latest tutorial sources: `cd ros2_ws/src/ros_tutorials && git pull`.
- **If you edit a file inside `ros_tutorials/`** (e.g. while working through a tutorial), that edit is only tracked by the upstream repo's local clone — you don't have push access to `ros/ros_tutorials`, and this repo won't back it up. To keep changes you care about, either commit them locally inside `ros_tutorials/` (so they survive on your machine) or copy the finished file into a package under `ros2_ws/src/` that belongs to *this* repo.

## Setup (first time on a machine)

ROS 2 Humble must already be installed. Add the following to `~/.bashrc`:

```bash
source /opt/ros/humble/setup.bash
export ROS_LOCALHOST_ONLY=1

# Switch ROS 2 subject workspace: ros_ws <subject_folder_name>
ros_ws() {
    local ws=~/subjects/$1/ros2_ws/install/setup.bash
    if [ -f "$ws" ]; then
        source "$ws"
        echo "Switched to $1"
    else
        echo "No built workspace found at $ws"
        echo "Run 'colcon build' from ~/subjects/$1/ros2_ws/ first"
    fi
}
```

You'll need to be added as a collaborator on `github.com/Elmacco/41068_Robotics_Studio_1` (or have your SSH key added) before you can clone/push. Ask whoever owns the repo to add your GitHub account.

Then clone this repo and build the workspace:

```bash
git clone git@github.com:Elmacco/41068_Robotics_Studio_1.git ~/subjects/41068_robotics_studio_1
cd ~/subjects/41068_robotics_studio_1/ros2_ws
colcon build
```

## Workflow for multiple people working in this repo

`41068_assignment` is now under active development by more than one person at once. The rules below are direct, not suggestions — the repo has already had feature work (SLAM/path planning, launch files) land straight on `main` with no branch or review, which is exactly what causes silent conflicts once two people are editing the same files. Follow these from now on.

**1. Never commit or push directly to `main`, except trivial doc-only edits (e.g. a typo in a `README.md`).** Every code change — a new node, a launch file edit, a world tweak, a dependency bump — goes through a branch and a PR, even if you're confident it won't conflict with anything. This is the actual rule, not a preference.

```bash
# 1. Get the latest main before starting ANY new work
git checkout main
git pull

# 2. Branch per task/feature — not per person, per person-per-day, etc.
git checkout -b thermal-camera        # e.g. thermal-camera, waypoint-follower, world-obstacles

# 3. Make edits, then stage deliberately
git add <files>                       # never `git add .`/`-A` — review what you're staging
git commit -m "Describe the change"

# 4. Pull main again and rebase/merge before pushing, so conflicts surface locally
git checkout main && git pull
git checkout thermal-camera && git rebase main   # or `git merge main` if you're not comfortable with rebase

# 5. Push and open a PR — do not merge your own PR without at least a skim from someone else
git push -u origin thermal-camera
```

**2. Before you start a session, always `git pull` on `main` and rebuild** (`colcon build --packages-select <pkg>`). Working from a stale tree is how you end up "fixing" something a teammate already fixed differently.

**3. Know the actual conflict hotspots in this package before you touch them:**

| File | Why it's a hotspot | Rule |
|---|---|---|
| `41068_assignment/launch/spawn_parrot.launch.py` | Every new sensor/node/feature adds a `Node(...)` here | Say in your team chat *before* you start editing it, not after you've already diverged |
| `41068_assignment/worlds/assignment_world.sdf` | Waypoints, obstacles, and heat-signature objects all live in the same file | Same — announce before editing, keep additions as separate `<include>`/`<model>` blocks so diffs stay small |
| `41068_assignment/CMakeLists.txt` / `package.xml` | Every new script or dependency touches these | Add your one line, don't reformat/reorder existing lines — keeps merges to single-line diffs instead of whole-file conflicts |
| `scripts/mission_waypoints.py` (`DEFAULT_WAYPOINTS`) | Shared route used by both waypoint scripts | Coordinate before changing the route itself |

**4. Extend, don't edit, the shared course package (`41068_ignition_bringup`).** If you need a new sensor, world asset, or config, add it in `41068_assignment` and reference/include the bringup package's files rather than modifying them directly (see `urdf_parrot/parrot_thermal.urdf.xacro` and `config/gazebo_bridge_parrot1_thermal.yaml` for the pattern). That package can also be overwritten by a future course update, and other teammates using the Husky depend on it staying as-is.

**5. `colcon build`/`install`/`log` output and `ros2_ws/src/ros_tutorials/` are gitignored** — safe to build before committing, and commits here never pick up anything from that nested repo (see [Two repositories in this workspace](#two-repositories-in-this-workspace)).

**6. If you land in a merge conflict, don't guess.** Conflicts in `spawn_parrot.launch.py` or the world file are usually two people's genuinely different additions, not one person being wrong — read both sides and combine them rather than picking one and discarding the other.
